# 罠通知モック

部品を買う前に、「通知の確実性」を支えるロジックが成り立つかを確かめるためのモック。
センサー側とサーバー側はブラウザの中でシミュレートしている。実機・サーバーはない。

## 開き方・テスト

- 画面：パソコンで `app/mock/index.html` をブラウザで開く（ネット接続不要。`logic.js` と同じフォルダに置くこと）。スマホで見るなら、公開されたものを開く。開き直すと初期状態に戻る。
- テスト：リポジトリの直下で `node app/mock/logic.test.js`。「11 tests passed」と出れば正常。

## 画面の見方

- 左（スマホでは上）が「猟師の画面」、右（下）が「現場のシミュレーター」（実機の代わり）。
- 状態は色だけでなく形と文字で区別する：赤い三角「作動」／黄色い菱形・点線「不明（通信なし）」／緑の丸「作動なし（確認済み）」。
- 初期状態：現在時刻 11/14 18:00、罠4基（沢沿い1、沢沿い2、尾根の分岐、杉林の箱罠。すべて例示）、生存確認の間隔 6時間。
- 罠ごとの操作ボタンは4基とも同じ名前なので、手順では「○○の行の」と書く。

## 机上確認手順

各シナリオの前に、シミュレーターの「初期状態に戻す」を押す。

### 1. 通常の作動（圏内）
1. 沢沿い1の行の「作動させる」を押す。
2. 見えれば正常：
   - 朝のまとめが「行く必要がある罠 1基／行かなくてよい罠 3基」になる。
   - 沢沿い1が赤い三角の「作動」になる。
   - 通知の履歴に「沢沿い1（例）：作動」が1件。「遅れて届いた」は付かない。

### 2. 圏外中の作動
1. 沢沿い1の行の「電波を切る」を押す（ボタンが「電波を戻す」に変わる）。
2. 同じ行の「作動させる」を押す。
3. 「1時間進める」を2回押す（2時間進む）。
4. 見えれば正常：通知の履歴は空のまま。沢沿い1の「未送信 1件（電波が戻るまで端末が保持）」と出る。猟師の画面は「作動なし（確認済み）」のまま（この時点では端末が圏外で何も届いていないため。シナリオ4の注意を参照）。
5. 「電波を戻す」を押す。
6. 見えれば正常：未送信が0件になり、通知に「沢沿い1（例）：作動」が出る。発生時刻は作動させた時刻（11/14 18:00）、受信は2時間後で、「遅れて届いた（2時間遅れ）」が付く。状態は「作動」になる。

### 3. 生存確認の途絶
1. 沢沿い2の行の「電波を切る」を押す。
2. 「6時間進める」を1回押す。まだ「作動なし（確認済み）」のまま（期限は6時間×1.5＝9時間）。
3. 「1時間進める」を2回押す（合計8時間）。まだ確認済みのまま。
4. 「1時間進める」を押す（合計9時間ちょうど）。まだ確認済み。さらに「10分進める」を押す。
5. 見えれば正常：沢沿い2が黄色い菱形の「不明（通信なし）」になり、通知に「沢沿い2（例）：通信が途絶えた」が1件出る。朝のまとめでは「行く」側に入る。
6. 「6時間進める」を数回押しても、通信が途絶えた通知は増えない。
7. 「電波を戻す」を押す。見えれば正常：「作動なし（確認済み）」に戻る。

### 4. 「通知がない＝かかっていない」と扱わない
1. 尾根の分岐の行の「電波を切る」を押し、続けて「作動させる」を押す。
2. 「翌朝6時まで進める」を押す（12時間進む）。
3. 見えれば正常：
   - 作動の通知は出ていない。
   - 尾根の分岐は「不明（通信なし）」で、朝のまとめの「行く必要がある罠」に入っている。
   - 「通信が途絶えた」の通知が1件ある。
- 注意：圏外になってから最大9時間（間隔×1.5）は、最後に確認した情報が残るため「作動なし（確認済み）」と表示され続ける。この間に作動しても、画面には出ない。各行の「最後の確認」時刻が、その表示の根拠。この窓の長さは生存確認の間隔で決まる（間隔を1時間にすれば1.5時間）。

### 5. 電池低下
1. 杉林の箱罠の行の「電池を10%にする」を押す。
2. 見えれば正常：電池が10%になり、「電池低下」の印が付く。通知に「電池低下」が1件。状態は「作動なし（確認済み）」のまま（別のフラグ）。
3. もう一度「電池を10%にする」を押し、「6時間進める」を押しても、電池低下の通知は増えない。
4. 電池を0%にする操作は画面にはない。10%にした後に電池が0になる場面は、ロジックのテスト（シナリオ5）で確認している。画面で確かめたい時は、杉林の箱罠の「電波を切る」を押して長く進めると、電池低下とは別に、通信途絶と同じ「不明」の動きを見られる。

補足：生存確認の間隔は「1時間」「6時間」「24時間」で切り替えられる（シナリオ8）。間隔を変えると各罠が生存確認を1回送り、そこから数え直す。「不明」になるまでの時間は、間隔の1.5倍。

## このモックで確かめられること／確かめられないこと

確かめられる：
- 「通知が来ない」と「かかっていない」を分ける考え方が、画面と朝のまとめに矛盾なく出せること。
- 圏外中の作動が、端末に保持され、電波が戻ると発生時刻つきで届き、遅れが分かること。
- 連番による重複排除、キューあふれ時に作動を残すこと、通信途絶・電池低下の通知が1回だけ出ること。
- 生存確認の間隔と、「不明」になるまでの時間の関係。

確かめられない：
- 電波の届き方（LoRaや携帯が現地で届くか、雨や霧での変化、再送の間隔）。ここでは電波は「あり／なし」だけで、送信は必ず成功する。
- 電池の実際のもち。電池は時間で減らず、ボタンで値を指定するだけ。
- センサーの取り付けと検知（罠の作動を本当に拾えるか、空はじきの判別、誤検知）。
- 通知の配信サービス（プッシュ、LINEなど）の信頼性と、届かなかった時に気づく方法。
- サーバーが落ちた場合、時計のずれ、複数人での利用。
- 電池0%の時の端末の実際の挙動（0%の手前で止まる、最後に何か送るなど）。

## 実物にする時の分担

| ロジックの部分 | センサー（ファームウェア） | サーバー | アプリ |
|---|---|---|---|
| イベント生成（作動、生存確認、電池低下、掛け直し）と連番・発生時刻 | 担当 | | |
| 未送信キューの保持、上限あふれ時の破棄ルール | 担当 | | |
| 電波がある時の送信、戻った時の再送 | 担当（送達確認を受けるまで保持する作りにする必要あり） | 受信と確認応答 | |
| 連番による重複排除 | | 担当 | |
| 状態判定（作動／作動なし／不明）、間隔×1.5の期限 | | 担当 | |
| 通信途絶・電池低下の検知と通知を1回出す制御 | | 担当（定期チェックが要る） | |
| 通知の履歴、「遅れて届いた」の判定 | | 記録と判定 | 表示 |
| 朝のまとめ、罠の一覧、状態の形・文字 | | | 担当 |
| 生存確認の間隔・電池しきい値の設定 | 受け取って反映 | 保持と配布 | 設定画面（このモックにはない） |
| 通知配信（プッシュ等） | | 送信 | 受信 |

モックで簡略化した点：実際のセンサーは、送信後に確認応答が来るまでイベントを消さない。確認応答が失われると同じイベントが二重に届くが、サーバーの重複排除で通知は1件になる（テストのシナリオ6）。
